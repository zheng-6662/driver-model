# 当前论文模型问题诊断：直观版摘要

## 一句话先说结论

你现在最该做的，**不是马上换一个更复杂的新模型**，而是先弄清楚：

> 当前主线已经学到了一部分“事件结构”，但还经常在 **峰值、边界、后段** 上对不准。  
> 所以下一步最值得先做的是：**先做误差归因，而不是先做结构升级。**

---

# 1. 你当前真正的主线是什么？

## 当前真实主线

```text
allphase_control_v2_context_full2s
        +
event-conditioned trajectory
        +
deterministic conditioned v2
```

## 不是当前主线中心的内容

```text
primary_control_v2 / d2 / d3
```

它们更像：
- 更早阶段的协议线
- 过渡探索线
- 或旧命名残留

而不是你现在最真实、最核心在推进的那条工程主线。

---

# 2. 当前主线像是卡在哪？

## 不是：模型完全不会预测

而更像是：

```text
趋势能学到一些
        ↓
但关键事件对齐还不稳定
        ↓
峰值错位 / 边界错位 / 后段失真
        ↓
最后看起来“平滑但不像真实人”
```

## 当前最像的瓶颈

### 第一层
- event / anchor / boundary 对齐问题
- peak timing 对不准
- tail 结构失真

### 第二层
- 不同样本的 reaction latency 可能不一致
- 不同驾驶员的风格和反应方式可能不同
- interaction 困难子集样本仍少且更复杂

### 第三层
- 多假设预测不是没潜力
- 而是 **oracle 有提升、top1 没接住**
- 说明当前问题更像 hypothesis selection / ranking 不稳

---

# 3. 为什么现在不建议你立刻换大结构？

因为现在直接改大结构，很容易把几件事混在一起：

```text
是标签定义有问题？
还是事件对齐有问题？
还是风格差异在作怪？
还是多解排序没做好？
还是模型真的太弱？
```

如果这些没先拆清楚：

- 你改了模型
- 指标可能变了
- 但你不知道到底是哪一层起作用

最后容易变成：

> 做了很多版本，结果越来越复杂，但结论不干净。

---

# 4. 当前最稳的推进顺序

## 不推荐的直觉路线

```text
发现后段失真
→ 立刻上更复杂模型
→ 再加 style 输入
→ 再加多假设
→ 再换任务
```

这个路线太容易乱。

---

## 现在更推荐的路线

```text
第 1 步：先做误差归因
        ↓
第 2 步：再看 latency / driver 差异是不是主因
        ↓
第 3 步：再看 multihyp 到底是生成问题还是排序问题
        ↓
第 4 步：最后才决定该改任务、改输入、还是改模型
```

---

# 5. 接下来最值得先做的 4 件事

## 第 1 位：事件对齐误差归因表

### 核心思想
先不改模型、不改协议，直接分析当前 conditioned v2 的错误是怎么来的。

### 重点看什么
- `main_peak_idx_mae`
- `boundary_shift_abs_err`
- `rmse_tail_abs_steer`
- turning count 相关误差
- interaction / non-interaction 切片
- driver / session 切片
- latency proxy 切片

### 你可以把它理解成

```text
先给当前错误“做体检”
而不是先给模型“换器官”
```

---

## 第 2 位：分驾驶员 / 分 session 误差分析

### 先做什么
- 看哪些驾驶员更容易错
- 看错的模式是否一致
- 看 driver 差异是不是主要通过 timing / boundary 体现

### 暂时不要先做什么
- 不要急着直接把 style / driver embedding 喂给模型

因为这会把：
- 任务问题
- 输入变化
- 身份记忆效应

混在一起。

---

## 第 3 位：multihyp 支线只做 gap 分析

### 当前现象
```text
oracle 好
但 top1 不稳
```

### 这说明什么
这更像：
- 多解空间可能真的存在
- 但当前 hypothesis ranking 没选对

### 所以现在它最适合做什么
- 做 failure analysis
- 看 selection 为什么失败

### 暂时不适合做什么
- 不适合直接接管主线

---

## 第 4 位：只有前面都支持时，才考虑新任务 / 新输入 / 新结构

比如：
- style-conditioned 输入
- latency-aware task variant
- 改 anchor / 改 future 定义
- 更正式的 multihyp 升级

这一步必须等前面证据够了再做。

---

# 6. 用一个更形象的比喻来理解现在的局面

你现在的模型状态，不像是：

```text
完全不会开车的人
```

更像是：

```text
已经能看懂大致路况
也知道什么时候该动方向
但经常会：
- 动作起点慢半拍或快半拍
- 峰值打得不对
- 后面的修正节奏乱掉
```

所以问题重点不是：

> “它有没有方向感？”

而更像：

> “它是不是在错误的时刻、错误的边界上做了还算合理的动作？”

这个区别非常重要。

---

# 7. 当前最不该急着做的事

## 暂时不要急着：

### 1. 直接换大模型结构
因为现在还没证明主因是结构瓶颈。

### 2. 直接上 style-conditioned 输入
因为还没先证明风格差异是不是独立主因。

### 3. 直接把 multihyp 扶正为主线
因为现在更像是 ranking 问题，不是已经成熟。

### 4. 一边改协议一边改模型再一起比较
因为这样最后结论很容易不干净。

---

# 8. 这轮诊断之后，我对你的问题的理解

你现在的问题可以更形象地改写成：

```text
当前主线不是“预测不到”
而是“预测得有点像，但关键地方总差一点”
```

而这“一点”主要体现在：
- 峰值时间
- 事件边界
- 后段修正
- 个体差异
- 多解选择

---

# 9. 我建议你下一步怎么看待这件事

先不要把它想成：

```text
我要不要换一个更牛的模型
```

而先把它想成：

```text
我要先查清：
当前模型到底在哪些样本、哪些时刻、哪种结构上出错
```

这个思路一旦对了，后面你再决定：
- 改协议
- 改输入
- 改模型
- 改评价口径

都会更稳。
