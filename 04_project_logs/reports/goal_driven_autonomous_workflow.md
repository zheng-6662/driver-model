# 目标驱动自治推进工作流

## 目的

这套工作流用于处理“用户不给每一步微指令，只给必须达到的目标”的任务。

目标不是让用户充当流程调度器，而是让 Claude / Codex 在明确边界内持续推进：

- 用户给目标
- 用户给验收口径
- 用户给红线
- Claude 负责收口、拆解、把控风险
- Codex 负责执行、检查、实现、验证
- 每次有实质进展先写项目日志
- 未达目标前，不因缺少“小步指令”而频繁中断

这套模式适用于：

- 多步代码实现
- 数据处理链修复
- 训练脚本改造
- 实验闭环验证
- 结果归因与 failure analysis
- 文献检索、证据整理与方案收口

## 本项目当前目标口径

对本项目而言，所谓“不要偏离目标”，优先是指不要偏离下面这个核心研究目标：

- 预测极限工况下的驾驶员行为
- 同时刻画与该行为耦合的车辆状态变化
- 当前阶段不要求完全精确复现每个点值
- 但要求整体趋势、方向与时序关系合理

这意味着当前阶段的可接受标准更接近：

- 预测趋势与真实趋势相似
- 方向盘转角、车辆状态等关键量不能出现明显过大的预测延时
- 不能出现系统性偏差过大
- 不能频繁出现方向相反或行为性质相反的预测

如果某条执行路线虽然局部指标好看，但明显偏离上述目标口径，例如：

- 只优化次要指标却让行为趋势更差
- 让延时更大
- 让方向性错误更严重
- 让输出波形看起来和真实行为机制越来越不像

那么这类路线应视为“偏离目标”的风险路线，而不是正常可继续深挖的主线。

## 最小输入

用户至少给出下面 3 项：

1. `目标`
2. `验收标准`
3. `红线`

推荐额外给出：

4. `资源边界`
5. `优先级偏好`
6. `不希望采用的方案`

如果用户没有写全，Claude 应先结合仓库上下文补齐合理默认值，并在日志或回复中明确说明假设，而不是因为缺少微小信息就停住。

## 默认边界

除非用户另行明确批准，本项目默认采用以下约束：

- 不删除用户现有文件
- 不进行破坏性清理
- 不用“先删再重建”的方式处理工作区
- 每次有实质进展，先写 `reports/project_progress_master.md`
- 压缩总结只能建立在详细日志已经落地的前提上
- 优先从 `datasetprocess/final_code` 与 active protocol 出发
- 优先保持 `subject-level split`、`anchor`、`horizon`、`online-only` 等核心 protocol 口径不被暗改
- 训练、评估、诊断默认使用 `predict2` conda 环境与 GPU，除非任务本身不适用或用户另有要求
- 训练规模应按风险和把握度决定，而不是机械固定为先做极小 smoke
- 如果目标、路径、输出位置和主要风险已经充分论证清楚，可以直接进入完整训练 / 完整测试

## 标准执行闭环

### 1. 目标收口

Claude 首先把用户目标收口成一个可执行 brief，至少明确：

- 要达到什么
- 什么算达标
- 什么不能碰
- 哪些文件最相关
- 需要什么证据证明达标

### 2. 风险预检

在真正执行前，Claude 先检查：

- 是否会触及删除、覆盖、迁移等破坏性动作
- 是否会改变 split / label / anchor / horizon
- 是否会引入数据泄漏、时间泄漏、未来信息泄漏
- 是否需要长时间 GPU 或大规模外部检索

若无高风险分叉，直接继续；若存在高风险分叉，再停下来请求用户拍板。

在本项目里，“真正高风险分叉”优先指：

- 可能让工作偏离“预测极限工况下驾驶员行为及车辆状态趋势”这一核心目标
- 可能为了某个局部问题牺牲更关键的趋势相似性、延时、方向一致性
- 可能让我们把大量时间耗在与主目标弱相关的小问题上
- 可能改变 protocol、论文主张或资源投入级别

### 3. 协作执行

默认按仓库现有协作结构推进：

- Claude 负责计划、收口、审查和风险判断
- Codex 负责具体执行、补丁、排查、验证、必要时资料检索

单轮 handoff 至少应写明：

- 任务范围
- 相关文件
- guardrails
- 验收标准
- 验证方式
- 日志义务
- 当前切片是否仍服务于主目标，而不是陷入局部牛角尖

### 4. 持续推进

如果目标尚未达成，但当前路径仍然有证据支撑，就继续迭代，而不是因为“用户还没给下一步指令”而停下。

持续推进时允许：

- 查本地文档
- 查现有 run / config / metrics
- 查协议文件
- 查论文或外部资料
- 做最小必要实现
- 做 smoke / 短跑 / 对照验证
- 做 bounded ablation

但持续推进不等于在同一个小问题上无限打转。默认采用“尝试预算”：

- 同一小问题、同一修复假设或同一类小旋钮，连续尝试达到 `3-4` 次后，原则上就应停止惯性深挖
- 只有在出现新的强证据、新机制假设或新的外部依据时，才允许继续在同一点追加尝试
- 如果 `3-4` 次后仍未明显改善，应把它降级为“当前非最优方向”，转去探索别的更可能影响主目标的路径

### 5. 达标或证据性停点

任务结束只有两种合法方式：

1. 已达到验收标准
2. 基于证据证明当前路径无法继续合理推进

第二种情况下，必须明确给出：

- 已尝试路径
- 失败证据
- 已排除原因
- 当前最优下一步

不能无依据地“感觉差不多”就停。

## 什么情况下必须停下来问用户

只有在下面这些情形下，才应该暂停并请求用户拍板：

- 需要删除、移动或覆盖用户重要文件
- 需要改变研究方向或论文主张
- 需要改变 split / label / anchor / horizon 等核心 protocol
- 需要明显增加 GPU / 时间 /外部服务成本
- 发现多个高代价路线，且后果差异显著
- 仓库里的规则彼此冲突，无法安全推断
- 当前路线虽然局部可优化，但明显开始偏离主目标口径

普通的小步实现、调试、检查、日志补充、短跑验证，不应反复打断用户。

同样地，普通的小问题在尝试 `3-4` 次后仍无明显进展时，也不应继续无休止地追问用户“要不要再试一次这个点”，而应先主动切换到别的方向，再带着证据回报。

## 日志要求

凡是以下工作，只要对项目有实质推进，都应写入 `reports/project_progress_master.md`：

- 命令执行
- 文件检查
- 代码修改
- 结果分析
- 实验复核
- 文献检索
- 方案收口
- 风险判断

每条详细记录至少包括：

- 执行主体
- Why
- What was checked / done
- What was found
- Recommended next step

如果本次工作改变了当前阶段判断，还应同步更新：

- 顶部“当前状态速览”
- “日期索引”
- “专题索引”

## 建议输出格式

当用户以后以这套模式下任务时，建议直接提供以下信息：

- `目标`
- `验收`
- `红线`
- `资源边界`
- `可接受的停点`

若用户只写了一句自然语言目标，也允许 Claude 先按仓库上下文补成上述结构，再开始推进。

对于本项目，建议把验收写得尽量贴近行为趋势，而不只是抽象的 loss 或单个数字。例如：

- 方向盘转角预测与真实行为趋势相似
- 关键状态预测不存在明显大延时
- 不出现大范围反向预测
- 结果足以支持“趋势正确、细节待继续优化”的阶段性判断

## 和现有命令体系的关系

本文件不是替代现有协作命令，而是作为它们的上位口径：

- `.claude/commands/codex-run.md`
- `.claude/commands/codex-workflow.md`
- `.claude/agents/codex-coordinator.md`
- `CLAUDE.md`

当用户明确表达“只给目标，你们自己持续推进直到达标”为主诉求时，应优先按本文件理解任务，而不是回到“做一步问一步”的模式。
